# Trading 评测框架

这个仓库是 Park Trading 线的汇总点。每个库要回答三个问题：**它在交易 pipeline 里是哪一环、它是否做到了自己声称的用途、证据是什么。** 评判标准先于打分存在，按环节不同，写在本文和 [`criteria.json`](criteria.json) 里；打分是从标准评级机械推导出来的，不是人工给的总分。

## 1. Pipeline：十个环节

交易系统是一条有顺序的流水线。每个产品覆盖其中一段，完整系统覆盖全部。

| # | 环节 | 输入 → 输出 |
|---:|---|---|
| 1 | 数据获取 `fetch` | 外部源 → 原始行情、基本面、新闻、事件 |
| 2 | 清洗与标准化 `clean` | 原始数据 → 统一 schema：代码、时区、复权、缺失处理 |
| 3 | 数据存档 `store` | 标准数据 → 可回放的历史库：增量、快照、版本 |
| 4 | 指标与特征 `indicator` | 历史库 → 指标、因子序列 |
| 5 | 策略与信号 `strategy` | 指标 → 买卖信号或目标仓位 |
| 6 | 回测 `backtest` | 策略 + 历史 → 绩效、成交、曲线 |
| 7 | 策略管理 `lifecycle` | 回测结果 → 注册、参数版本、paper→live 晋级、下线 |
| 8 | 风控 `risk` | 目标订单 → 通过、拒绝或缩量：仓位、敞口、熔断 |
| 9 | 执行与券商 `execute` | 通过的订单 → 委托、成交、持仓与资金对账 |
| 10 | 监控与看板 `monitor` | 全链路状态 → 人能快速看懂并干预 |

顺序即依赖：3 依赖 1、2；4 依赖 3；6 依赖 4、5；9 必须经过 8；10 贯穿全程。Equity Research 是 4、5 的人工或半自动形态，为策略或人提供研判；Knowledge & Collections 是参考资料，不进 pipeline，不评测。

每个产品的卡片上有一行环节矩阵，每格取值：● 实测跑通 · ◐ 源码可见未实测 · ○ 无 · · 不在其角色内。

## 2. 目录类别对应的环节与目标

| 类别 | 环节 | 目标 |
|---|---|---|
| Data | 1–3 | 取得正确、及时、完整的交易数据，最好免费，下游能直接接入 |
| Equity Research | 4–5（研判） | 为买卖决策提供可核验、可复现的研判 |
| Trading Strategy | 4–6 | 策略与指标知识库全面、正确、能直接送进回测 |
| Trading Infra | 6–9 | 回测→风控→执行的骨架可靠，组件可单独替换 |
| Dashboard | 10 | 人能快速、清晰地找到信息并干预 |
| Full Trading System / Agent | 1–10 | 有完整骨架，先解耦再重耦，能跑通一次 paper 闭环 |
| Knowledge & Collections | — | 不评测 |

## 3. 每类的评判标准

评级只有五种：✅ 做到 · 🟡 部分 · ❌ 未做到 · ⬜ 未验证 · — 不适用。定义见 `criteria.json` 的 `rating_scale`。每条标准都要附一句证据和至少一张截图或一个记录文件；没有证据就只能是 ⬜。

### Data

| 标准 | 权重 | 怎么判 |
|---|---:|---|
| D1 正确 | 25 | 与第二来源交叉核对一致；错误和空值有明确信号，不是静默 200 或空表 |
| D2 及时 | 20 | 声明的时效与实测一致；能区分成交时间和取数时间 |
| D3 完整 | 20 | 市场、资产类别、字段、历史深度、缺失率符合声明 |
| D4 免费可得 | 15 | 无 key 可用范围、限流、许可；免费层能否撑起日常研究 |
| D5 可接入 | 20 | 输出是标准形态（OHLCV、DataFrame、稳定 JSON）；清洗与存档要么内置，要么边界清楚 |

### Equity Research

| 标准 | 权重 | 怎么判 |
|---|---:|---|
| R1 输入可靠 | 20 | 数据来源清楚、时效有标注 |
| R2 方法可复现 | 25 | 估值、筛选、评级是规则、模板或脚本；纯 LLM 自由发挥记部分 |
| R3 输出可核验 | 25 | 报告里的数字能对回原始数据；不一致有记录 |
| R4 覆盖 | 15 | 市场与研究类型符合声明 |
| R5 可接入 | 15 | 结论结构化、可被策略或人快速消费；安装与凭证门槛可控 |

### Trading Strategy

| 标准 | 权重 | 怎么判 |
|---|---:|---|
| S1 覆盖 MECE | 25 | 趋势、均值回归、突破、波动率、事件、结构形态、市场状态；指标族成体系 |
| S2 正确 | 25 | 与参考实现或自身基准一致；批量与逐根一致；无未来函数 |
| S3 可回测接入 | 20 | 能输出标准信号给回测器，或自带回测且结果可导出 |
| S4 参数化可扩展 | 15 | 参数外置、可组合、新增策略成本低 |
| S5 复现稳定 | 15 | 安装、测试套件、确定性输出 |

### Trading Infra

| 标准 | 权重 | 怎么判 |
|---|---:|---|
| I1 回测引擎正确 | 20 | 事件顺序、费用与滑点模型、报告完整；合成数据可复现 |
| I2 执行接口 | 25 | paper、testnet、live 分层；订单类型；成交、持仓、资金回读与对账 |
| I3 风控钩子 | 15 | 下单前检查可插入；fail-closed |
| I4 解耦可替换 | 20 | 数据源、策略、券商适配器边界清晰 |
| I5 稳定与测试 | 20 | 测试套件、错误态、版本稳定 |

### Dashboard

| 标准 | 权重 | 怎么判 |
|---|---:|---|
| V1 清晰 | 25 | 信息层级明确，首屏有关键信息，找到目标步骤少 |
| V2 时效标注 | 20 | 数据日期与延时可见；过期不冒充实时 |
| V3 可操作 | 20 | 筛选、自选、告警、切换周期真实可用 |
| V4 可接入 | 20 | 能消费我们自己的数据或作为组件嵌入；无登录门槛 |
| V5 稳定 | 15 | 加载、错误态、跨端 |

### Full Trading System / Agent

| 标准 | 权重 | 怎么判 |
|---|---:|---|
| F1 环节覆盖 | 25 | 十个环节实际存在多少；源码可见与实测跑通分开计 |
| F2 解耦 | 20 | 组件有边界和接口，能单独替换 |
| F3 重耦跑通 | 25 | 端到端一次 paper 闭环：数据→信号→风控→模拟成交→持仓回读 |
| F4 风控与安全 | 15 | fail-closed、密钥隔离、没有默认实盘 |
| F5 运维交付 | 15 | 安装、配置、监控、失败恢复 |

## 4. 分数怎么来

- 每条标准：得分 = 权重 × 评级值（做到 1、部分 0.5、未做到 0、未验证 0）。
- 不适用的标准从分母剔除：总分 = Σ得分 ÷ Σ适用权重 × 100，四舍五入。
- 同时报告**已验证比例**：评级为做到、部分或未做到的标准权重 ÷ 适用权重。未验证比例高的产品分数低，是因为没测到，不是因为差。
- 已验证比例低于 40% 的产品不进排名，列在"证据不足"区。适用权重低于 60% 的产品也不进排名：本类标准多数对它没意义，说明它不属于这一类，卡片上给出建议类别。
- 同分并列同一名次，如 1、2、2、2、5；并列内按已验证比例、再按名称排列。
- 排名只在同一类别内有意义。跨类别看环节矩阵，不看分数。
- 分数不代表盈利能力、生产成熟度或全部功能可用。

## 5. 卡片格式

每个产品一张卡，字段固定、顺序固定，由 `scripts/render-hub.py` 从 `assessments/*.json` 生成，人工不直接编辑生成页。

1. 标题：排名、名称、分数、已验证比例
2. 环节矩阵（十格）
3. **声称**：产品自己 README 的用途，一句话
4. **实测**：是否做到（✅ 🟡 ❌ ⬜）加一句话
5. 标准表：标准 · 权重 · 评级 · 证据（含截图链接）
6. **适合** / **不适合**
7. **未验证** 与 **下一步最值得验证**
8. 证据：截图数、实测记录、实际试用版本、目录锁；如建议改归类别，在此说明

## 6. 证据规则

- 只用本仓库已有的证据：`evaluations/<类别>/<日期>/` 下的 findings、README、evidence、screenshots。不新增截图，除非某产品证据实在不足以判定核心用途。
- 每条评级至少引用一张截图（相对路径）或一个记录文件。截图数量只是证据留存量，不是功能覆盖率。
- 未测不等于不支持；缺 key、账户、开市时段、产品阻断统一记 ⬜ 并写明原因。
- 声称来自产品 README 或目录描述；实测结论只绑定实际试用版本。
- 分类建议只是评测意见，canonical 分类与锁在 Park OS 维护。

## 7. 数据源与生成

- `criteria.json`：环节、类别、标准、权重、评级尺度。
- `assessments/<类别>.json`：每个产品的卡片数据。字段：`repo`、`name`、`catalog_category`、`evaluated_as`、`evidence_dir`、`tested_revision`、`interface`、`markets`、`claimed`、`delivered{status,summary}`、`stages{...}`、`criteria{ID:{rating,evidence,shots[]}}`、`best_for`、`not_for`、`unverified[]`、`next`、`suggested_category`、`hero`、`notes`。一个产品只有一张完整卡片，放在 `evaluated_as` 对应的类别；若它在目录类别文件里另有占位条目，标 `stub: true`，只作指向。
- `python3 scripts/render-hub.py` 生成 `evaluations/README.md`（pipeline 总览）、`evaluations/<类别>/README.md`（类别页）和根 README 的 `<!-- HUB:START -->` 区块。
- `python3 scripts/check-hub.py` 校验：目录中每个非 Knowledge 条目都有卡片、权重合法、分数推导一致、引用的截图存在、链接可达、无本机路径。

按日期归档的目录（如 `data/2026-09-27/`）是那一轮的原始证据，其中的 0–100 分是首轮人工分，已被本框架的推导分取代；保留不改，供复核。
